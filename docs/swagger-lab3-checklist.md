# Ручная проверка лабораторной 3 через Swagger

Сценарий проверяет вход, JWT, роли, доступ к ресурсам, создание пользователей,
отсутствие паролей в ответах и применение изменений прав к уже выданным токенам.
Ожидаемые результаты сверены с текущим кодом. Это инструкция для ручного прогона;
сам прогон через работающий стек при подготовке инструкции не выполнялся.

## 1. Подготовка

1. Запусти актуальную сборку: `docker compose up -d --build`.
2. Открой http://localhost:8080/swagger-ui.html.
3. В выпадающем списке выбирай документ нужного сервиса:

   | Запросы | Документ Swagger |
   |---|---|
   | `/api/v1/auth/...`, `/api/v1/users/...` | `user-service` |
   | Проекты, участники, мониторы, теги, инциденты | `monitor-service` |
   | `/api/v1/monitors/{id}/results` | `check-service` |
   | Каналы и уведомления | `notification-service` |

4. Для запросов с токеном нажимай **Authorize** и вставляй только значение
   `access_token`, без слова `Bearer`, кавычек и остального JSON.
   При смене пользователя сначала нажми **Logout**, затем вставь его токен.
   При переключении документа проверь авторизацию: в показанном Swagger запросе
   должен быть заголовок `Authorization: Bearer ...` с нужным токеном.
5. Перед проверкой входа и после экспериментов с испорченным, истёкшим или
   заблокированным токеном очищай **Authorize**. Иначе плохой токен может привести
   к отказу ещё до выполнения публичной ручки входа.

Используй отдельные тестовые аккаунты из сценария. Начального супервайзера
оставь активным и с ролью `SUPERVISOR`.

Во всех примерах используется суффикс `01`. Для повторного прогона замени его
в email, slug и названиях тестовых данных на `02`, `03` и так далее.

Записывай ID из ответов и токены:

| Обозначение | Что сохранить |
|---|---|
| `S_TOKEN` | JWT начального супервайзера |
| `A_ID`, `A_TOKEN` | ID и JWT оператора A, владельца первого проекта |
| `B_ID`, `B_TOKEN` | ID и JWT оператора B |
| `V_ID`, `V_TOKEN` | ID и JWT просмотрщика |
| `P1`, `P2` | ID проектов операторов A и B |
| `M1` | ID монитора в проекте P1 |
| `C1` | ID канала в проекте P1 |

**В JSON ниже 101, 102 и 103 — примеры ID операторов A, B и просмотрщика.
Заменяй их реальными ID.** Обозначения `P1`, `M1` и другие в путях также заменяй
числами из своих ответов. Сохранённые JWT используй только в пределах их срока
действия; перед проверками изменения роли и блокировки получи свежий токен.

## 2. Публичный вход и ошибки JWT

Сначала очисти **Authorize**.

| № | Запрос / действие | Ожидается |
|---|---|---|
| 2.1 | `GET /api/v1/projects` без JWT | `401` |
| 2.2 | `GET /api/v1/auth/me` без JWT | `401` |
| 2.3 | Вход с правильным email супервайзера и неправильным непустым паролем | `401` |
| 2.4 | Вход с отсутствующим email `missing-lab3-01@example.com` и непустым паролем | `401`, такое же общее сообщение об ошибке, как в 2.3 |
| 2.5 | Вход с email `not-an-email` | `400`: ошибка валидации формата |
| 2.6 | Вход с настоящими данными супервайзера из `.env` | `200` |

Для входа используй `POST /api/v1/auth/login`:

```json
{
  "email": "supervisor@example.com",
  "password": "ПОДСТАВЬ_ПАРОЛЬ_ИЗ_ENV"
}
```

Если в `.env` другой `SUPERVISOR_EMAIL`, подставь его. Сохрани `access_token`
как `S_TOKEN`. Ответ должен содержать `token_type: "Bearer"` и положительное
`expires_in` — по умолчанию 900 секунд.

Установи `S_TOKEN` через **Authorize** и вызови `GET /api/v1/auth/me`.
Ожидается `200`, твой профиль и роль `SUPERVISOR`.
В ответе не должно быть ни `password`, ни `password_hash`, ни `secret_hash`.

Дополнительные проверки JWT:

| № | Действие | Ожидается |
|---|---|---|
| 2.7 | Вместо JWT авторизоваться строкой `invalid` и вызвать `GET /api/v1/projects` | `401` |
| 2.8 | В копии настоящего JWT изменить первый символ третьей части, после второй точки, и вызвать тот же GET | `401`: неправильная подпись |

После проверок восстанови исходный `S_TOKEN`.

## 3. Создание тестовых пользователей

Все успешные запросы этого раздела выполняются с `S_TOKEN` в `user-service`.

### 3.1. Оператор A через Users

`POST /api/v1/users`:

```json
{
  "email": "operator-a-lab3-01@example.com",
  "password": "Lab3-Test-Password-2026!",
  "full_name": "Swagger Operator A",
  "role": "OPERATOR"
}
```

Ожидается `201`, заголовок `Location`, роль `OPERATOR`. Сохрани `id` как `A_ID`.
Пароля и хэша в ответе быть не должно.

### 3.2. Оператор B через Authentication

`POST /api/v1/auth/register` с тем же форматом тела, но следующими данными:

```json
{
  "email": "operator-b-lab3-01@example.com",
  "password": "Lab3-Test-Password-2026!",
  "full_name": "Swagger Operator B",
  "role": "OPERATOR"
}
```

Ожидается `201` и `Location`. Сохрани `B_ID`.

### 3.3. Просмотрщик с ролью по умолчанию

`POST /api/v1/users` — поле `role` намеренно отсутствует:

```json
{
  "email": "viewer-lab3-01@example.com",
  "password": "Lab3-Test-Password-2026!",
  "full_name": "Swagger Viewer"
}
```

Ожидается `201` и роль `VIEWER`. Сохрани `V_ID`.

### 3.4. Негативные проверки создания

| № | Кто | Действие | Ожидается |
|---|---|---|---|
| 3.4.1 | Супервайзер | Повторить создание A с тем же email | `409` |
| 3.4.2 | Супервайзер | Создать новый email с паролем `short` | `400` |
| 3.4.3 | Супервайзер | Создать пользователя с email `not-an-email` | `400` |
| 3.4.4 | Супервайзер | Создать новый email с `"role": "SERVICE"` | `400`: этой роли нет в пользовательском enum |
| 3.4.5 | Без JWT | Создать новый email через `/api/v1/users` | `401` |
| 3.4.6 | Без JWT | Создать новый email через `/api/v1/auth/register` | `401` |

Для проверок используй остальные поля из валидного примера. В ошибках не должно
быть исходного пароля, хэшей или SQL-деталей.

### 3.5. Получение пользовательских токенов

По очереди, с очищенным **Authorize**, войди через `POST /api/v1/auth/login`
как A, B и просмотрщик. Пароль у всех трёх: `Lab3-Test-Password-2026!`.
Сохрани полученные `A_TOKEN`, `B_TOKEN`, `V_TOKEN`.

## 5. Проекты и зависимость результата от пользователя

В документе `monitor-service` с токеном A вызови `POST /api/v1/projects`:

```json
{
  "owner_id": 101,
  "name": "Swagger Project A",
  "slug": "swagger-project-a-01"
}
```

Здесь 101 замени на `A_ID`. Ожидается `201`, сохрани ID как `P1`.

С токеном B создай второй проект:

```json
{
  "owner_id": 102,
  "name": "Swagger Project B",
  "slug": "swagger-project-b-01"
}
```

Здесь 102 замени на `B_ID`. Ожидается `201`, сохрани `P2`.

| № | Кто | Действие | Ожидается |
|---|---|---|---|
| 5.1 | A | `GET /api/v1/projects` | В `content` есть P1, отсутствует P2 |
| 5.2 | B | Тот же GET | Есть P2, отсутствует P1 |
| 5.3 | Просмотрщик | Тот же GET | Пустой `content`, `total_elements: 0` |
| 5.4 | Супервайзер | Тот же GET | Доступны оба проекта; при наличии других записей учитывай пагинацию |
| 5.5 | B | `GET /api/v1/projects/P1` | `403` |
| 5.6 | A | `GET /api/v1/projects/P2` | `403` |
| 5.7 | Просмотрщик | `GET /api/v1/projects/P1` | `403`, членство ещё не выдано |
| 5.8 | A | Создать проект с `owner_id` B и новым валидным slug | `403` |
| 5.9 | Просмотрщик | Создать проект на своё имя с новым валидным slug | `403` |
| 5.10 | A | Повторить создание своего P1 с тем же slug | `409` |
| 5.11 | A | Создать проект со своим `owner_id`, но slug `Bad Slug!` | `400` |

`total_elements` относится к доступным текущему пользователю проектам.

## 6. Монитор и канал: свои ресурсы и чужой ID

С токеном A создай монитор: `POST /api/v1/projects/P1/monitors`:

```json
{
  "name": "Swagger Health 01",
  "url": "http://monitor-service:8080/actuator/health",
  "http_method": "GET",
  "interval_sec": 10,
  "timeout_ms": 5000,
  "expected_status": 200,
  "tags": []
}
```

Ожидается `201`. Сохрани `M1`. Адрес выше предназначен для Docker Compose;
для локального запуска укажи адрес, доступный процессу `check-service`.

В документе `notification-service` с токеном A создай канал:
`POST /api/v1/projects/P1/channels`:

```json
{
  "type": "EMAIL",
  "target": "swagger-lab3-01@example.com"
}
```

Ожидается `201` и `Location`. Сохрани `C1`. Для прогона проверки прав доставка
уведомлений может оставаться выключенной, как задано по умолчанию.

Выполни следующие запросы сначала с токеном A, затем с токеном B.
**B пока не состоит в P1.**

| Запрос | A | B |
|---|---|---|
| `GET /api/v1/projects/P1/monitors` | `200` | `403` |
| `GET /api/v1/monitors/M1` | `200` | `403` |
| `GET /api/v1/monitors/M1/results` (`check-service`) | `200` | `403` |
| `GET /api/v1/projects/P1/channels` (`notification-service`) | `200` | `403` |
| `GET /api/v1/channels/C1` (`notification-service`) | `200` | `403` |

История проверок может пока быть пустым JSON-массивом — это успешный `200`.
Эти кейсы проверяют, что подстановка чужого ID не открывает ресурс, в том числе
в другом микросервисе.

Дополнительно с токеном A:

| Действие | Ожидается |
|---|---|
| Повторить создание того же EMAIL-канала с тем же target в P1 | `409` |
| Создать новый монитор с `url: "ftp://example.com"` | `400` |
| Создать новый монитор с `interval_sec: 1` | `400` |

## 7. Просмотрщик: чтение разрешено, запись запрещена

С токеном A вызови `POST /api/v1/projects/P1/members`:

```json
{
  "user_id": 103
}
```

Замени 103 на `V_ID`. Ожидается `201`; повторение — `409`.

Переключись на `V_TOKEN`. Все пять GET-запросов из таблицы раздела 6,
а также `GET /api/v1/projects/P1` теперь должны вернуть `200`.
В списке проектов просмотрщика появится P1.

Проверь запреты записи с тем же `V_TOKEN`:

| Запрос | Тело | Ожидается |
|---|---|---|
| `POST /api/v1/projects/P1/monitors` | Валидный монитор из раздела 6 с другим name | `403` |
| `DELETE /api/v1/monitors/M1` | Без тела | `403` |
| `PUT /api/v1/projects/P1` | `{"name":"Viewer rename"}` | `403` |
| `PUT /api/v1/projects/P1/owner-notifications` | `{"enabled":false}` | `403` |
| `POST /api/v1/projects/P1/channels` | Новый валидный EMAIL target | `403` |

| `DELETE /api/v1/channels/C1` | Без тела | `403` |

После запретов с токеном A проверь, что M1 и C1 существуют, имя проекта
и настройки канала остались прежними.

## 8. Участник-оператор и владелец имеют разные права

С токеном A добавь B в P1 через `POST /api/v1/projects/P1/members`
с телом `{"user_id":102}`, подставив `B_ID`. Ожидается `201`.

С токеном B:

| Действие | Ожидается |
|---|---|
| `GET /api/v1/projects/P1` | `200` |
| Прочитать историю M1 и каналы P1 | `200` |
| Создать монитор в P1 с новым именем и валидным телом из раздела 6 | `201` |
| `PUT /api/v1/channels/C1`, тело `{"target":"member-lab3-01@example.com","enabled":false}` | `200` |
| `PUT /api/v1/projects/P1`, тело `{"name":"Member rename"}` | `403` |
| `PUT /api/v1/projects/P1/owner-notifications`, тело `{"enabled":false}` | `403` |
| `DELETE /api/v1/projects/P1` | `403` |
| Добавить участника через `POST /api/v1/projects/P1/members` с валидным user_id | `403` |

С токеном A изменение имени проекта и `owner-notifications` должны вернуть `200`.
С токеном супервайзера те же операции также разрешены.

## 10. Понижение роли для уже выданного JWT

Перед началом получи свежий `A_TOKEN`, пока A имеет роль `OPERATOR`.
Этот токен сохраняй неизменным до завершения раздела.

С `S_TOKEN` вызови `PUT /api/v1/users/A_ID/role`:

```json
{
  "role": "VIEWER"
}
```

Ожидается `200`. Теперь со **старым A_TOKEN**, в котором ещё записан OPERATOR:

| Действие | Ожидается |
|---|---|
| `GET /api/v1/auth/me` | `200`, актуальная роль `VIEWER` |
| `GET /api/v1/projects/P1` | `200`: A остаётся владельцем и может читать |
| Создать новый монитор в P1 с валидным телом | `403` |
| Изменить C1 валидным PUT из раздела 8 | `403` |

С `S_TOKEN` верни A роль через тот же PUT с `{"role":"OPERATOR"}`.
После восстановления роли со старым A_TOKEN создание нового монитора в P1
должно снова вернуть `201`, пока JWT не истёк.

Этот сценарий использует токен, изначально выданный оператору. При повышении роли
токен, изначально выданный VIEWER, может быть отклонён gateway на операциях записи:
gateway использует роль из JWT. Для такой ситуации нужен новый вход.

## 11. Блокировка и удаление пользователя

Перед началом получи свежий `B_TOKEN`, пока B активен. Он уже участник P1.

С `S_TOKEN` вызови `PUT /api/v1/users/B_ID`:

```json
{
  "full_name": "Swagger Operator B",
  "status": "BLOCKED"
}
```

Ожидается `200`. С сохранённым B_TOKEN:

| Действие | Ожидается |
|---|---|
| `GET /api/v1/auth/me` | `401` |
| `GET /api/v1/projects/P1` | `401` |
| `GET /api/v1/monitors/M1/results` | `403` |
| `GET /api/v1/projects/P1/channels` | `403` |

Различие кодов соответствует текущей реализации: user-service и monitor-service
отклоняют аккаунт при аутентификации, а check-service и notification-service
получают отказ от удалённой проверки прав. Во всех случаях данные недоступны.

Очисти **Authorize** и попробуй войти под B с правильным паролем: ожидается `401`.
С `S_TOKEN` восстанови B через PUT с тем же `full_name` и `"status":"ACTIVE"`.
Со старым B_TOKEN `GET /api/v1/projects/P1` снова должен вернуть `200`, если срок
действия JWT ещё не закончился.

Теперь с `S_TOKEN` выполни `DELETE /api/v1/users/B_ID` → `204`.

| Действие | Ожидается |
|---|---|
| С `S_TOKEN` получить `GET /api/v1/users/B_ID` | `404` |
| Со старым B_TOKEN получить `/api/v1/auth/me` | `401` |
| Войти под B с правильным паролем, предварительно очистив Authorize | `401` |

Удаление мягкое: аккаунт становится неактивным; его числовой ID сохраняется для
ссылок в проектах. Проверяй удаление на тестовом B, а не на начальном супервайзере.

## 12. Дополнительные проверки

| Кто | Действие | Ожидается |
|---|---|---|
| Супервайзер | `GET /api/v1/users/999999999`, если такой ID отсутствует | `404` |
| Супервайзер | `GET /api/v1/projects/999999999`, если такой ID отсутствует | `404` |
| Супервайзер | `GET /api/v1/services/check-service/health` при здоровом стеке | `200` |
| A / просмотрщик | Тот же запрос состояния сервиса | `403` |
| Любой пользователь | Попытка использовать просроченный JWT для `/api/v1/auth/me` | `401` |

Для последней проверки сохрани свежий токен и подожди его `expires_in` плюс
90 секунд, чтобы учесть временной допуск валидатора, затем используй именно
сохранённую строку. Изменение `exp` вручную проверяет подделку подписи, а не
естественное истечение срока.

Внутренние `/internal/**` скрыты из OpenAPI и не маршрутизируются gateway.
Обычный Swagger-прогон не проверяет напрямую получение служебного токена и отказ
служебному JWT на пользовательском API. Эти случаи покрываются автоматическими
тестами; успешные запросы истории и каналов косвенно проверяют межсервисную
аутентификацию при удалённой проверке доступа.

Через Swagger можно проверить отсутствие пароля в ответах. Фактическое хранение
только хэшей проверяется кодом, тестами или чтением БД, а не формой JSON-ответа.

## 13. Очистка тестовых данных

С `S_TOKEN` удали только созданные этим прогоном данные:

1. `DELETE /api/v1/projects/P1` → `204`.

зависимых сервисов и их готовность. Такой ответ не подтверждает прохождение
проверки роли или принадлежности ресурса.
