# Report-service: требования и план реализации

Статус: **проект первой версии**, сервис ещё предстоит реализовать. Документ фиксирует
объём работ для лабораторной № 4 и решения, необходимые для интеграции с текущим проектом.

## 1. Назначение и границы

`report-service` хранит готовые отчёты, загруженные пользователями в проект, и по запросу
автоматически формирует отчёты о мониторинге. Первая версия поддерживает CSV и PDF для обоих
сценариев: загрузки готового файла и фоновой генерации. Доступны список и метаданные,
скачивание и удаление. Содержимое хранится в MinIO, метаданные и задания — в собственной
PostgreSQL-базе `report_db`.

Генерация запускается пользователем и выполняется автоматически в фоне. Расписание по cron
и периодическая отправка по почте в первую версию не входят. История проверок в
`check-service` сейчас поддерживает пагинацию, но не фильтрацию по периоду: для генерации
будут добавлены внутренние API сервисов — владельцев данных. Сервис отчётов не читает их
базы напрямую.

MinIO запускается в Compose в односерверном режиме с постоянным томом `minio-data`.
Требование о трёх брокерах относится к уже реализованному кластеру Kafka. Для MinIO
кластер из трёх узлов в первой версии не требуется.

## 2. Функциональные требования

1. Пользователь загружает неизменяемый файл отчёта, прикрепляя его к существующему проекту.
2. Пользователь с правом записи запрашивает генерацию CSV или PDF по периоду и мониторам
   проекта. Сервис сохраняет задание и формирует файл в фоне.
3. Участник проекта с правом чтения получает список, статус, метаданные и готовое содержимое.
4. Пользователь с правом записи удаляет отчёт или отменяет его генерацию через удаление;
   физическая очистка выполняется с повторами.
5. При удалении проекта отчёты и задания становятся недоступны и очищаются из MinIO.
6. Сервис регистрируется в Eureka, получает настройки от Config Server и доступен через
   Gateway и общий Swagger UI.

Тело файла передаётся по HTTP через Gateway и `report-service`. Kafka передаёт события об
изменении ресурсов, не содержимое файлов. В первой версии публичный bucket и выдача
предподписанных ссылок клиентам не используются.

## 3. REST API

Все пути доступны через Gateway. Метаданные содержат идентификатор отчёта и проекта, источник
`UPLOADED` или `GENERATED`, автора, формат, статус и время создания. После готовности доступны
также имя файла, размер и SHA-256. У задания генерации возвращаются параметры периода,
время запроса, время генерации и доступные границы чтения источников. У `FAILED` указывается
безопасный код ошибки, без stack trace и секретов. До готовности ещё неизвестные поля — `null`.
Внутренний ключ объекта и учётные данные MinIO не возвращаются.
Имя генерируемого файла задаётся сервисом: `report-{reportId}.csv` или `report-{reportId}.pdf`.

| Метод и путь | Назначение | Успешный ответ |
|---|---|---|
| `POST /api/v1/projects/{projectId}/reports` | Загрузить `multipart/form-data`, поле файла `file` | `201 Created`, `Location: /api/v1/reports/{reportId}` и метаданные `READY` |
| `POST /api/v1/projects/{projectId}/reports/generations` | Поставить генерацию в очередь | `202 Accepted`, `Location: /api/v1/reports/{reportId}`, метаданные нового задания `QUEUED` |
| `GET /api/v1/projects/{projectId}/reports` | Список отчётов и заданий проекта | `200 OK`, JSON-массив и заголовки пагинации |
| `GET /api/v1/reports/{reportId}` | Метаданные и статус, включая ожидающие и завершившиеся ошибкой задания | `200 OK` |
| `GET /api/v1/reports/{reportId}/content` | Скачать готовый файл | `200 OK`, поток файла; `409` до `READY` |
| `DELETE /api/v1/reports/{reportId}` | Принять удаление | `202 Accepted`, удаление объекта продолжается в фоне |

Пагинация: `page=0`, `size=20` по умолчанию, `1 ≤ size ≤ 50`. Сортировка стабильная:
по времени создания и ID, от новых к старым. Заголовки ответа списка — `X-Total-Count`
и `X-Has-Next`. Запрос с недопустимой пагинацией возвращает `400`.

В список входят загруженные отчёты, ожидающие и активные задания генерации, готовые и
завершившиеся ошибкой отчёты; записи `DELETING` скрыты. Допустимы фильтры `status` и
`source`. GET метаданных возвращает `200` для любого видимого состояния, включая
`QUEUED`, `GENERATING`, `UPLOADING` и `FAILED`. Содержимое доступно только при `READY`;
в остальных видимых состояниях скачивание возвращает `409 Conflict`. После принятия
удаления отчёт скрыт из списка, а GET возвращает `404`. Повторный DELETE во время удаления
после проверки прав возвращает `202`; после окончательного удаления записи — `404`.

Внешние JSON-поля используют принятую в проекте стратегию `snake_case`; имена Java-полей
могут оставаться в `camelCase`. Пример запроса на формирование отчёта; `monitor_ids`
необязателен — без него выбираются все мониторы проекта. Для заданного непустого списка все
ID должны принадлежать проекту:

```http
POST /api/v1/projects/42/reports/generations
Authorization: Bearer <JWT>
Idempotency-Key: 2d613f9a-913a-44c8-893f-13ed1e34b801
Content-Type: application/json

{
  "from": "2026-10-01T00:00:00Z",
  "to": "2026-10-02T03:00:00+03:00",
  "format": "CSV",
  "monitor_ids": [11, 12]
}
```

`format` принимает `CSV` или `PDF`. `from` и `to` обязательны, содержат часовой пояс и
нормализуются в UTC; период полуоткрытый `[from, to)`, `from < to ≤ requestTime`.
Явный пустой `monitor_ids: []` отклоняется с `400`. Если выбран вариант «все мониторы» и
при приёме известно, что в проекте их нет, возвращается `400`; если это обнаружено уже
работником, задание получает `FAILED/NO_MONITORS`. Монитор без проверок при этом остаётся
строкой отчёта с пустыми метриками доли и времени ответа.
До ответа `202` сервис транзакционно сохраняет UUID отчёта, параметры, автора, время запроса
и `QUEUED`. Он не ждёт сборки отчёта в HTTP-запросе. Клиент опрашивает
`GET /api/v1/reports/{id}` и после `READY` скачивает `/content`; `FAILED` возвращается в
метаданных с безопасным кодом причины.

`Idempotency-Key` необязателен, но рекомендуется. Его область — пользователь, проект и ключ.
В той же транзакции сохраняется хеш канонических параметров: UTC-период, формат и
упорядоченный набор выбранных мониторов либо признак «все мониторы». Повтор с теми же
параметрами возвращает тот же `reportId` и актуальное состояние; использование ключа с
другими параметрами даёт `409 Conflict`. Привязка хранится без истечения, пока существуют
метаданные отчёта. После удаления записи остаётся tombstone привязки на настраиваемое время
`REPORT_IDEMPOTENCY_TOMBSTONE_TTL` (по умолчанию 24 часа). Повтор с действующим ключом
удалённого отчёта даёт `409 REPORT_DELETED`, не создавая новое задание; после истечения
tombstone ключ можно использовать для нового задания. Срок привязки покрывает жизнь задания.
После окончательного `FAILED` новая генерация создаётся новым запросом с другим ключом либо
без него; отдельный API ручного повтора не требуется.
Неверные параметры и отсутствие прав отклоняются до постановки задания; ошибки источников
во время работы отражаются состоянием `FAILED` или планируемым повтором.

Скачивание отправляет `Content-Disposition: attachment` с безопасно закодированным исходным
именем, проверенный `Content-Type` и `Content-Length`. Поток MinIO закрывается при успешном
завершении, ошибке или отключении клиента. Файл не собирается целиком в `byte[]` приложения.
Если MinIO недоступен до отправки заголовков, возвращается `503`. При обрыве после отправки
`200` изменить статус уже нельзя: сервис закрывает поток и безопасно фиксирует ошибку в логе,
а клиент обнаруживает неполную передачу по длине и при необходимости проверяет SHA-256.

## 4. Форматы и ограничения

| Настройка | Значение первой версии |
|---|---|
| Форматы загружаемых и генерируемых файлов | `.csv` в UTF-8 и `.pdf` |
| Минимальный размер содержимого | Один байт; пустой файл отклоняется с `400` |
| Максимальный размер содержимого | 10 MiB; значение настраивается |
| Максимальный размер multipart-запроса | 12 MiB по умолчанию, с запасом на границы и заголовки |
| Имя файла | Обязательное непустое имя; отделяется от пути и безопасно отображается |
| Object key загрузки | `projects/{projectId}/reports/{reportId}`, где `reportId` — UUID |
| Object key генерации | `projects/{projectId}/reports/{reportId}/attempts/{attemptId}`; новая попытка получает новый UUID |

Проверяются расширение и содержимое: CSV должен декодироваться как UTF-8, PDF должен иметь
ожидаемую сигнатуру в начале. Базовая проверка сигнатуры PDF не является антивирусной
проверкой и не доказывает корректность всего документа. `Content-Type` от клиента сам по
себе не подтверждает формат. Сервис определяет канонический тип по разрешённому расширению
и проверенному содержимому: `text/csv; charset=UTF-8` для CSV и `application/pdf` для PDF.
Эти типы сохраняются в метаданных и устанавливаются при скачивании.

У части `file` multipart-запроса допустимы отсутствующий `Content-Type`,
`application/octet-stream` или тип, совместимый с определённым форматом: `text/csv` с
отсутствующей кодировкой или `charset=UTF-8` для CSV и `application/pdf` для PDF. Явно
несовместимый тип или иная кодировка дают `415 Unsupported Media Type`. Пустое содержимое
отклоняется с `400 Bad Request`; неверный UTF-8 или сигнатура — с `400`. Сравнение типов и
имени кодировки выполняется без учёта регистра.

Переданное пользователем имя файла не используется как путь или ключ объекта; управляющие
символы и небезопасные имена отклоняются. Обработка данных потоковая. Допускается ограниченный
временный файл multipart, который очищается после запроса и при восстановлении после сбоя.
Размеры проверяются и на Gateway, и в сервисе; допустимый файл должен проходить через
обе границы. Проверка ограничений применяется также к потокам без доверенного заголовка
`Content-Length`. При разборе значений Spring `MB` означает 2²⁰ байт согласно
[Spring DataUnit](https://docs.spring.io/spring-framework/docs/6.2.x/javadoc-api/org/springframework/util/unit/DataUnit.html).

Машиночитаемые и человекочитаемые ошибки совместимы с текущим API проекта:

| Ситуация | HTTP |
|---|---|
| Нет действительного JWT | `401 Unauthorized` |
| Нет права на проект | `403 Forbidden` |
| Проект или отчёт не найден; отчёт удаляется | `404 Not Found` |
| Некорректный запрос, период, выбор мониторов, имя, пагинация, пустой файл или неверное содержимое | `400 Bad Request` |
| Превышен лимит размера | `413 Payload Too Large` |
| Неподдерживаемый формат или несовместимый `Content-Type` части файла | `415 Unsupported Media Type` |
| Скачивание отчёта до готовности; повтор idempotency key с другими параметрами | `409 Conflict` |
| Нельзя проверить права или выполнить необходимую операцию с MinIO | `503 Service Unavailable` |

`201` возвращается только после подтверждённого сохранения объекта и фиксации `READY` в БД.
Если MinIO временно недоступен при уже принятом DELETE, ответ остаётся `202`: задача очистки
сохранена и будет повторена.

Генерация ограничивается настройками: период не более 31 дня, не более 100 выбранных
мониторов, не более 100 000 строк источников суммарно, страницы до 50 записей, не более
5 минут на попытку и два одновременно работающих задания на экземпляр по умолчанию. Эти значения можно
изменить конфигурацией. Результат подчиняется тому же лимиту 10 MiB, что и загруженный файл.
Проверяемые заранее ограничения отклоняются при запросе; превышение, выявленное работником,
завершает задание `FAILED` с кодом `LIMIT_EXCEEDED`. Молчаливое усечение данных или
публикация частичного отчёта как `READY` запрещены.

## 5. Состав автоматически созданного отчёта

Запрос формирует один сводный отчёт по проекту и выбранным мониторам. Данные в обоих
форматах рассчитываются по одной модели и одним правилам:

- ID и имя проекта; ID, имя и URL каждого выбранного монитора;
- UTC-период `[from, to)`, время запроса и формирования;
- число проверок, число `SUCCESS` и отдельные количества `BAD_STATUS`, `TIMEOUT`,
  `CONNECTION_ERROR`;
- доля успешных проверок: `100 × SUCCESS / total`; при отсутствии проверок значение
  отсутствует (`null`/`N/A`), а строка монитора всё равно присутствует;
- минимальное, среднее и максимальное `responseMs` по всем результатам, где
  `responseMs != null`, включая значение `0` и независимо от типа исхода; если таких
  значений нет — `null`/`N/A`;
- число инцидентов за период, количества по `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` и число
  инцидентов, открытых на момент конца периода.

Проверка входит в период при `checkedAt >= from AND checkedAt < to`. Инцидент включается,
если его интервал пересекает период: `startedAt < to AND (resolvedAt IS NULL OR
resolvedAt > from)`. Для уже включённых инцидентов открытым **на момент `to`** считается
инцидент с `resolvedAt IS NULL OR resolvedAt > to`; закрытый ровно в `to` считается
закрытым. Инцидент, начатый ровно в `to` или закрытый ровно в `from`, в выборку не входит.
Доля успешных проверок — метрика проверок, а не вычисление uptime; длительность простоя в
первой версии не рассчитывается. При накоплении сохраняется достаточная точность; при
представлении среднее и процент округляются до двух знаков по `HALF_UP` одинаково в CSV/PDF.

CSV содержит одну строку агрегатов на монитор и стабильный заголовок в таком порядке:

```text
project_id,project_name,monitor_id,monitor_name,monitor_url,period_from_utc,period_to_utc,requested_at_utc,generated_at_utc,total_checks,success_count,bad_status_count,timeout_count,connection_error_count,success_ratio_percent,response_ms_min,response_ms_avg,response_ms_max,incidents_total,incidents_low,incidents_medium,incidents_high,incidents_critical,incidents_open_at_end
```

Для пустых метрик CSV использует пустое поле. Кодировка — UTF-8, разделитель — запятая;
запятые, кавычки и переносы строк внутри полей корректно экранируются. Пользовательский
текст, начинающийся с `=`, `+`, `-` или `@`, предваряется апострофом для безопасного открытия
в электронных таблицах; числовые метрики остаются числовыми значениями. PDF содержит те же
поля и метрики и может дополнительно приводить таблицу инцидентов. PDF поддерживает кириллицу
встроенным шрифтом, разбиение на страницы и повторение заголовков таблиц; библиотека и версия
фиксируются после проверки доступности и лицензии.

## 6. Источники данных генерации

Сбор данных идёт по HTTP как запрос/ответ с service credentials и `ROLE_SERVICE`. Двоичные
данные отчёта и запрос/ответ к источникам не передаются через Kafka; для локального
долговечного задания новый Kafka-топик не требуется. Три существующих бизнес-топика и их
настройки остаются прежними.

Добавляются внутренние API с закрытым доступом через сервисную сеть:

| Владелец | Пример маршрута | Назначение |
|---|---|---|
| monitor-service | `POST /internal/report-data/projects/{projectId}/selection` | Проверить проект и выбранные ID, вернуть метаданные проекта и страницами метаданные мониторов |
| monitor-service | `POST /internal/report-data/projects/{projectId}/incidents/search` | Вернуть инциденты выбранных мониторов, интервалы которых пересекают `[from, to)` |
| check-service | `POST /internal/report-data/checks/search` | Вернуть проверки выбранных мониторов с `checkedAt >= from AND checkedAt < to` |

Каждый запрос содержит проект, выбранные ID или признак «все» для начального selection,
период, `limit ≤ 50` и при продолжении непрозрачный `cursor`. Ответ страницы имеет вид
`{items, next_cursor, has_next, source_captured_at, upper_id}`; `upper_id`/другие границы чтения
фиксируются источником при начале обхода и сохраняются вместе с отчётом. Если продолжения
нет, `next_cursor` равен `null`; ответ selection также содержит метаданные `project`.
Cursor принадлежит источнику и привязан к проекту, выбору мониторов или признаку «все»,
периоду и границам чтения; его нельзя применить к другой выборке. Сортировка —
стабильная keyset-пагинация по ID, например `id > lastId AND id <= upperId`, а не offset по
меняющимся таблицам. Точные DTO, индекс и механизм защиты cursor определяются при
реализации и проверяются тестами.

В начале попытки фиксируется наблюдаемый список подходящих мониторов, не более 100 по
умолчанию, включая случай «все мониторы»; затем он используется в обоих источниках. Если хотя
бы один явно запрошенный монитор не относится к проекту, задание не принимается либо, при
обнаружении изменения во время работы, завершается ошибкой. Источники проверяют принадлежность
запрошенных мониторов проекту. У check-service нет локальной таблицы проектов: он проверяет
состав через доверенный API monitor-service с сервисной авторизацией, не читая чужую БД.

Для каждой попытки фиксируются время наблюдения и верхние границы источников; новые проверки
с ID выше зафиксированного предела в неё не попадают. Эти границы **не создают общего
атомарного снимка** между сервисами: поздний commit или backfill с уже выделенным ID, изменение
инцидента и удаление данных во время обхода могут повлиять на результат. Метаданные и файл
содержат время запроса/формирования, а метаданные — границы и время наблюдения источников.
Повторная попытка может увидеть другие данные. Если источник исчез или остаётся недоступным
после ограниченных повторов, задание завершается `FAILED`, частичный результат не публикуется.

Агрегация выполняется постранично: не нужно загружать все проверки и инциденты в память.
При сбое страницы текущая попытка перезапускается целиком с чистыми агрегатами и новыми
границами; повтор страницы не должен дважды увеличить счётчики. Буферы рендера PDF и
временное хранилище также ограничены. Превышение лимита результата или числа строк даёт
`FAILED/LIMIT_EXCEEDED` без усечения.

## 7. Модель и хранение

Отдельная БД `report_db` содержит метаданные и задания, но не файл. У отчёта есть:

- `id` — UUID; `project_id`, `created_by` — числовые внешние идентификаторы;
- источник `UPLOADED`/`GENERATED`, имя, внутренний ключ объекта, формат, MIME-тип, размер,
  SHA-256; ещё неизвестные до готовности значения допускают `null`;
- статус, `created_at`, `updated_at`, безопасный код ошибки, данные активной попытки;
- для генерации — нормализованный период, выбор мониторов, время запроса/формирования,
  наблюдаемые границы источников, число попыток и время следующей попытки;
- lease-токен и срок lease задания/очистки, а также сведения о ключах объектов попыток.

Таблица ключей идемпотентности хранит область `(user_id, project_id, key)`, хеш параметров,
`report_id` и срок хранения. Уникальное ограничение и сохранение ключа вместе с новым
заданием обеспечивают корректную обработку одновременных одинаковых запросов.
`project_id` и `created_by` не имеют внешних ключей в другие базы сервисов. В БД создаются
индексы для списка по проекту, очереди заданий и очереди очистки; enum сохраняется строкой.
Потребуются также таблицы обработанных событий inbox и маркеров удалённых проектов.

Bucket `reports` закрыт для публичного чтения. Для `report-service` создаётся отдельная
учётная запись с доступом только к нужному bucket; root-данные нужны инициализации и не
передаются как рабочие данные приложения. UUID ключа формируется сервером и не содержит
исходного имени. SHA-256 вычисляется по самим байтам; ETag объекта не считается SHA-256.

### Состояния

```text
UPLOADED:  UPLOADING ──> READY ──> DELETING
                 └─────> FAILED ──> DELETING
GENERATED: QUEUED ──> GENERATING ──> READY ──> DELETING
              ↑          ├────────> FAILED ──> DELETING
              └──────────┘ временный сбой: повтор с задержкой
Любое видимое состояние ── удаление отчёта или проекта ──> DELETING
```

После подтверждённой очистки объекта и завершения нужных проверок запись `DELETING` может
быть удалена. `FAILED` или `DELETING` хранит достаточно данных для повторной очистки, даже
если предыдущий процесс завершился аварийно. Метаданные неуспешного задания `GENERATED`
сохраняются для опроса; очистка файлов его попыток не удаляет запись задания. Изменения
состояния выполняются условно с учётом текущего состояния и токена попытки; устаревший
обработчик не может вернуть запись в `READY`.

### Загрузка и восстановление

Общей транзакции PostgreSQL и MinIO нет; сетевые операции и передача файла не удерживают
транзакцию БД. Объект MinIO не переносится с предположением об атомарном переименовании.
Сценарий:

1. Проверить пользователя, существование проекта и право записи. В короткой транзакции
   под общей блокировкой проекта создать `UPLOADING` с UUID ключа и токеном попытки,
   если локальный маркер удаления проекта отсутствует.
2. Передать файл в MinIO вне транзакции БД, вычислить размер и SHA-256. Ограничить время
   обращения к хранилищу. Каждая попытка загрузки использует новый идентификатор отчёта и
   собственный неизменяемый ключ объекта; ключи старых попыток повторно не используются.
3. В короткой транзакции под той же блокировкой проекта повторно проверить маркер удаления,
   состояние и токен попытки, затем записать метаданные и `READY`.
4. При ошибке или невозможности финализации сохранить задачу очистки и повторять её с
   задержкой. Если MinIO подтвердил `putObject`, а фиксация БД не удалась, файл не выдаётся
   как `READY`; его ключ остаётся доступным для восстановления и очистки.

### Фоновая генерация и восстановление

1. При приёме запроса проверить актуального пользователя, право записи, существование
   проекта, формат и границы периода; записать задание `QUEUED` и idempotency key одной
   короткой транзакцией. После commit вернуть `202`.
2. Работник атомарно выбирает готовое к выполнению задание через
   `FOR UPDATE SKIP LOCKED`, переводит его в `GENERATING`, сохраняет уникальные `attemptId`,
   lease-токен и срок lease, затем завершает транзакцию. Несколько экземпляров делят работу.
3. Перед началом каждой попытки и повтора проверить актуальность прав автора. Сохранить
   неизменяемый ключ этой попытки, зафиксировать список мониторов и границы чтения,
   постранично собрать агрегаты и сформировать CSV или PDF. Сетевые вызовы источников,
   рендеринг и `putObject` идут вне транзакции БД. Работник продлевает lease heartbeat-ом;
   потеря lease запрещает публикацию результата старой попыткой.
4. Перед публикацией ещё раз проверить права и существование проекта. Затем в короткой
   локальной транзакции под блокировкой проекта проверить отсутствие маркера удаления,
   действующие состояние, lease и токен; только текущая попытка записывает метаданные файла
   и переводит отчёт в `READY`. Внешняя проверка прав и локальная транзакция не образуют
   общей атомарной операции: отзыв права сразу после проверки может состязаться с commit.
5. Временная ошибка источника или MinIO возвращает задание в `QUEUED` с backoff и временем
   следующей попытки, максимум три попытки по умолчанию, включая первую. Исчерпание попыток даёт `FAILED`
   с безопасным кодом. Отозванное право — `FAILED/ACCESS_REVOKED`, превышение лимита —
   `FAILED/LIMIT_EXCEEDED`; эти ошибки не повторяются бесконечно. При удалённом проекте
   задание переходит в `DELETING`. Отдельная очередь очистки удаляет объекты неудачных
   попыток, сохраняя метаданные `FAILED` для пользователя.

Состояние и параметры хранятся в БД, поэтому после перезапуска задача продолжится или
будет повторена после истечения lease. Первая версия начинает повторную попытку с нуля;
durable checkpoint отдельных страниц не требуется. Новый `attemptId` создаёт новый объектный
ключ даже при том же `reportId`. Если старый работник всё же дописал объект после потери
lease, условная финализация не разрешит `READY`, а компенсация и периодическая сверка удалят
его ключ. Удаление отчёта в `QUEUED` или `GENERATING` возвращает `202`, отзывает lease и
устанавливает `DELETING`; поздняя попытка не может восстановить отчёт.

Фоновый обработчик при старте и периодически выбирает незавершённые операции. Несколько его
экземпляров используют блокировку/lease для выбора работы и делают вызовы MinIO вне коротких
транзакций; неуспешное удаление повторяется с backoff. Наличие `READY` без объекта выявляется
при скачивании или проверкой согласованности. Если MinIO подтвердил отсутствие ключа, сервис
условно переводит запись из `READY` в `FAILED` с внутренней причиной `OBJECT_MISSING`; проверка
текущего состояния не позволяет отменить параллельное удаление. До отправки заголовков
скачивание возвращает `503`, а не пустой файл. Затем GET метаданных возвращает `200` со
статусом `FAILED`, а GET содержимого — `409`.
Один только таймаут или недоступность MinIO не доказывает отсутствие объекта и не меняет статус.
Запись `FAILED` с причиной `OBJECT_MISSING` сохраняется для диагностики до восстановления или
явного удаления; она не удаляется автоматически задачей очистки неуспешных загрузок.

Истёкший lease не доказывает, что старый сетевой `putObject` уже остановился. Поэтому после
удаления проекта или истечения попытки поздний загрузчик или работник не может зафиксировать
`READY` и пытается удалить свой объект. Периодическая сверка объектов bucket с метаданными дополнительно
находит поздно появившиеся и осиротевшие ключи, в том числе если процесс упал до компенсации.
При сверке учитываются активные попытки и период ожидания для выполняющегося `putObject`;
неиспользуемые ключи удаляются с повтором. Маркер удалённого проекта сохраняется. Удаление
ключа идемпотентно; нельзя считать отсутствие объекта при единственной проверке доказательством,
что отставшая операция загрузки уже не запишет его позже.

## 8. Доступ и безопасность

Используются JWT/JWKS и действующая модель пользователей проекта:

| Роль | Условие и операции |
|---|---|
| `VIEWER` | Доступный проект: список, метаданные, скачивание |
| `OPERATOR` | Доступный проект: чтение, загрузка, генерация и удаление |
| `SUPERVISOR` | Операции над существующими проектами |

На каждой операции проверяются активность пользователя, существование проекта и право на
чтение/запись. Проверка существования обязательна и для `SUPERVISOR`: действующий вызов
проверки прав может разрешить ему доступ без проверки наличия ресурса. ID автора берётся из
проверенного JWT, а не из пользовательского поля запроса. Ошибка проверки прав закрывает доступ
с `503`; сведения о файле не выдаются до проверки прав.

Для генерации право проверяется при приёме запроса, перед каждой попыткой и повтором, а
также непосредственно перед публикацией. Если разрешение отозвано, новый `READY` не
публикуется при обнаружении отзыва; при изменении права после последней внешней проверки
сохраняется указанная выше граница между удалённой проверкой и локальной транзакцией.
`VIEWER` может опрашивать состояние доступного проекта и скачать готовый отчёт.

Адаптер межсервисного доступа использует service credentials и защищённый
`/internal/access/project/{id}` в monitor-service. Для MVC используется синхронный адаптер
к `ResourceAccessClient` через порт; JWT и реактивный `RemoteAccess` не передаются в домен
или сценарии приложения. Новый `REPORT_SERVICE_CLIENT_SECRET` регистрируется в bootstrap и
конфигурации user-service и передаётся в Compose как отдельный секрет.

## 9. Удаление проекта и транспорт

Существующий `RESOURCE_EVENTS_TRANSPORT` управляет доставкой событий удаления; значение по
умолчанию — `http`. Настройка должна совпадать у monitor-, check-, notification- и
report-service. Переключение применяется после перезапуска всех участников; перед сменой
нужно обработать накопленный outbox прежнего транспорта. Автоматического fallback между
Kafka и HTTP нет.

**Kafka:** report-service условно создаёт listener при
`integration.resource-events.transport=kafka`. Он читает существующий `resources.events.v1`
в отдельной группе `report-resource-events-v1`; другие группы продолжают получать свои копии.
`ProjectDeleted` обрабатывается, `MonitorDeleted` подтверждается без удаления отчётов проекта.
Новые топики и уведомления о загрузке отчёта в первой версии не требуются.

Для `ProjectDeleted` одна локальная транзакция сохраняет `eventId` в inbox, устанавливает
маркер удалённого проекта и переводит отчёты и задания всех состояний в `DELETING`, отзывая
их lease. Общая блокировка проекта согласует это действие с созданием и завершением загрузки
или генерации. Kafka offset подтверждается после
commit локальных изменений; самих файлов может коснуться последующая фоновая очистка.
Повтор события не создаёт повторную работу с другим смыслом. При временной ошибке БД запись
повторяется; некорректный контракт обрабатывается действующей схемой DLT
`resources.events.v1.dlt`.

**HTTP:** защищённая `ROLE_SERVICE` ручка `POST /internal/integration/events` вызывает тот же
сценарий и inbox. В HTTP fan-out monitor-service добавляется вызов report-service только для
`ProjectDeleted` с исходным `eventId`. Ошибка доставки возвращается отправителю, чтобы его
outbox повторил попытку; успешные повторные вызовы check- и notification-service безопасны
благодаря их inbox. Задания на проверку `/internal/monitors/due` остаются через HTTP.

## 10. Clean Architecture

```text
report-service/
  domain/                  Report, ReportStatus, ReportSource и правила переходов
  application/
    usecase/               UploadReport, GenerateReport, GetReportMetadata,
                           DownloadReport, ListReports, DeleteReport
    port/                  ReportRepository/JobQueue, ObjectStorage, ProjectAccessPort,
                           ReportDataSource, ReportRenderer, Clock
  adapters/
    in/web/                multipart, генерация задания, DTO и HTTP-ответы
    in/kafka/              преобразование и передача событий в сценарий
    out/persistence/       JPA, ReportEntity, очередь/lease и преобразование модели
    out/minio/             MinIO Java SDK через ObjectStorage
    out/http/              права и чтение данных через monitor- и check-service
    out/render/            CSV и PDF, работа со шрифтами и ограниченными буферами
  config/                  создание и связывание компонентов
```

Домен — обычные Java-типы без JPA и Spring; `ReportEntity` отдельно от доменной модели.
Сценарии зависят от портов, принимают собственные команды и ограниченный поток/метаданные,
а не `MultipartFile`, `JpaRepository`, `MinioClient`, `KafkaTemplate` или `Jwt`. Управление
транзакциями, часы и внешние вызовы подключаются через порты или инфраструктурную композицию.
Правила состояний проверяются отдельно; одних названий пакетов недостаточно. Приведение всех
существующих сервисов к Clean Architecture остаётся отдельной работой лабораторной.

Кроме того, сервис получает действующие настройки Config Server, Eureka, JWKS и service token.
Числа для генерации в таблице — параметры планируемой первой реализации, а не существующие
в проекте настройки. Ключ идемпотентности хранится, пока существуют метаданные отчёта, и
ещё заданное время после их удаления. Это не означает автоматического удаления готового файла.
Пароли и секреты не хранятся в исходном коде и не попадают в журнал. Значение лимита в байтах
должно действительно составлять 10 × 1024 × 1024; запросу выделяется 12 × 1024 × 1024 байт.
Таймаут Gateway/Circuit Breaker и multipart-лимиты согласуются с допустимой длительностью
загрузки и скачивания. Перед передачей/чтением объектного потока следует убедиться, что
Gateway не буферизует файл целиком без необходимости.

Изменения инфраструктуры:

- `settings.gradle.kts`, `report-service/build.gradle.kts` и общий `Dockerfile`: включить и
  собрать новый модуль и его зависимости;
- `docker/postgres/create-databases.sql`: идемпотентно создать `report_db`; Liquibase владеет
  схемой нового сервиса;
- `docker-compose.yml`: MinIO с собственным томом, healthcheck и совместимыми правами записи;
  идемпотентный `minio-init` создаёт приватный bucket и учётную запись, затем стартует сервис;
- `config-server/src/main/resources/config-repo/report-service.yml`: БД, лимиты, MinIO,
  безопасность и параметры фоновых задач/генерации;
- `monitor-service` и `check-service`: защищённые внутренние API данных с фильтрацией по
  периоду, проверкой проекта, keyset-cursor и ограничением размера страницы;
- конфигурация Gateway: явные маршруты reports и API docs перед общим маршрутом
  monitor-service; добавить сервис в список Swagger UI и настроить fallback;
- Kafka overlay: согласовать зависимость report-service от инициализации Kafka при запуске
  overlay; базовый HTTP-стек запускается без Kafka.

Версии образа MinIO и Java SDK фиксируются после проверки доступности и совместимости в ходе
реализации. `latest` и непроверенное наличие конкретного образа не считаются воспроизводимой
конфигурацией. Контейнер приложения сохраняет модель запуска без root.

## 12. План реализации

Тесты для каждого этапа добавляются вместе с кодом, а не откладываются до конца.

1. **Каркас и инфраструктура.** Добавить модуль, `report_db`, Config Server, Eureka,
   MinIO, bucket init и постоянный том. Готово: Compose-конфигурация валидна, сервис
   поднимается с БД и приватным bucket без Kafka в HTTP-режиме.

   без инфраструктуры.
3. **Адаптеры БД и MinIO.** Добавить Liquibase, репозиторий и потоковую работу с объектами.
   Готово: тесты PostgreSQL и MinIO подтверждают запись, чтение, удаление и SHA-256.

## 13. Тесты и критерии приёмки

- Unit: состояния, валидация файлов, выбор портов и обработка ошибок. Проверить нулевое
  количество проверок, `null` и `0` в `responseMs`, типы ошибок, округление и запрет
  трактовать долю успешных проверок как uptime.
- Метрики: инцидент открыт до начала периода, начат/закрыт точно в `from` или `to`, закрыт
  после периода, ещё открыт; отдельные количества по severity и open-at-end соответствуют
  формулам. Проверить периоды с часовыми поясами и нормализацию UTC.
- Рендер: единые метрики в CSV/PDF, CSV с запятыми, кавычками, переносами и формульными
  префиксами пользовательского текста; PDF с кириллицей, встроенным шрифтом и несколькими
  страницами. В проекте без проверок существующие мониторы остаются в отчёте.
- Интеграционные тесты с настоящими PostgreSQL и MinIO через Testcontainers: загрузка,
  чтение, байтовое совпадение и SHA-256, удаление, сохранность после перезапуска, а также
  построение CSV и PDF работником и проверка их содержимого.
- MockMvc и Gateway: multipart и поток скачивания, JWT, роли, доступ другого проекта,
  `Location`, имена файлов, лимиты 10/12 MiB и заголовки пагинации. Проверить создание
  задания, `202`, опрос `QUEUED`/`GENERATING`/`FAILED` через `200`, скачивание `409`
  до готовности, успешное скачивание и повторный/конфликтующий `Idempotency-Key`.
- Запрос генерации: будущий или пустой период, отсутствие часового пояса, пустой список ID,
  чужой монитор, отсутствие мониторов, превышение 31 дня или 100 мониторов, неавторизованный
  пользователь и доступ `VIEWER` только на чтение/опрос. Все настраиваемые пределы,
  включая 100 000 строк, 5 минут, 10 MiB результата и ограничение конкуренции, проверяются;
  результат при превышении лимита никогда не публикуется частичным.
- Источники: фильтрация проверок `[from,to)`, пересечение интервалов инцидентов, защита
  сервисных маршрутов и проверки проекта, ключевой cursor и лимит страницы 50. Во время
  постраничного чтения добавляются проверки: новые ID за границей чтения не попадают в
  попытку; тесты не предполагают отсутствия позднего commit или общего снимка БД.
- Валидация: пустой файл, опасное имя, неподдерживаемое расширение, несовместимый MIME,
  некорректный UTF-8 или сигнатура отклоняются с указанными статусами; отсутствующий MIME и
  `application/octet-stream` допускаются после проверки содержимого. Проверяется недоступность
  MinIO и сервиса проверки прав, а также обнаружение отсутствующего объекта `READY`.
- Сбои источников, рендера и после `putObject`, до commit БД и при удалении; повтор после
  перезапуска, ограничение попыток, inbox rollback/dedup. Проверить отзыв прав, удаление
  проекта во время генерации/загрузки, отмену `QUEUED`/`GENERATING`, потерю lease и позднюю
  запись устаревшей попытки: готовые данные не возрождаются, объект очищается. При ошибке
  источника частичный результат не становится `READY`; повтор с начала попытки после сбоя
  на странице не удваивает агрегаты уже прочитанных данных.
- Реальные Kafka KRaft + PostgreSQL + MinIO: потребление `ProjectDeleted`, повтор события,
  отдельная группа и последующая очистка. HTTP-режим проверяется без работающей Kafka,
  включая повтор доставки из outbox monitor-service.
- Существующие три основных топика Kafka сохраняют три партиции и фактор репликации 3;
  добавление report-service не меняет обработку check- и notification-service.
- `./gradlew check` проходит с покрытием строк не менее 70% по действующему правилу проекта;
  новые классы не исключаются из покрытия ради прохождения порога. Также проверяются
  `docker compose config` и сквозной запуск. Обязательная демонстрация: загрузить готовый
  файл, создать отдельные задания CSV и PDF по данным двух сервисов, опросить до `READY`
  и скачать оба отчёта с корректными метриками; проверить восстановление после остановки.
