# Лабораторная работа 3: авторизация

API защищён Spring Security Resource Server. Клиент входит по email и паролю и передаёт
полученный JWT в заголовке `Authorization: Bearer <access_token>`. HTTP-сессии, Basic Auth
и публичная регистрация не используются.

## Запуск и первый супервайзер

Скопируйте `.env.example` в `.env` (если файл уже есть — дополните его):

```dotenv
JWT_TTL=PT15M
SERVICE_JWT_TTL=PT5M
MONITOR_SERVICE_CLIENT_SECRET=replace-with-a-random-secret-at-least-32-characters
CHECK_SERVICE_CLIENT_SECRET=replace-with-another-random-secret-at-least-32-characters
NOTIFICATION_SERVICE_CLIENT_SECRET=replace-with-a-third-random-secret-at-least-32-characters
SUPERVISOR_EMAIL=supervisor@example.com
SUPERVISOR_PASSWORD=replace-with-a-strong-password
```

Для каждого клиента сгенерируйте отдельный секрет командой `openssl rand -hex 32`.
Значения по умолчанию в compose предназначены только для локальной разработки.
Закрытый ключ RS256 создаётся самим user-service и хранится в Docker volume
`user-signing-keys`; другим сервисам он не передаётся. Старый `JWT_SECRET` больше не используется.

```bash
docker compose up -d --build
```

При первом запуске `user-service` после импорта старых аккаунтов создаёт супервайзера с указанными учётными данными,
только если супервайзеров ещё нет. Уже существующая учётная запись не получает новые
права автоматически. Если bootstrap email занят обычным пользователем, задайте другой
email. Повторный запуск не меняет пароли и роли существующих супервайзеров. После
создания начального аккаунта `SUPERVISOR_PASSWORD` можно убрать из окружения.

Пользователей через REST API может создавать только супервайзер. Bootstrap — отдельный
механизм подготовки пустой системы, а не публичная ручка создания пользователей.

## Границы сервисов

`user-service` владеет базой `user_db`, таблицами пользователей и служебных клиентов,
хэшами паролей, глобальными ролями, блокировками, входом и подписью JWT.
`monitor-service` владеет проектами, участниками и правами на ресурсы проектов.
Владелец проекта — это `owner_id`, участник — `user_id`, без JPA-связей с удалённым `User`.
Имена и email участников загружаются одним пакетным запросом на страницу, максимум 50 ID.

## Перенос существующих пользователей

Для обновления стека предыдущей версии сначала соберите образы и приостановите запись:

```bash
docker compose build
docker compose stop gateway monitor-service check-service notification-service
docker compose up -d --no-deps --wait config-server
docker compose up -d --wait user-service
docker compose up -d --wait
```

По умолчанию compose задаёт `USER_MIGRATION_SOURCE_URL`, указывающий на старую базу
monitor-service. Импорт выполняется до создания первого супервайзера и до готовности
user-service. Он сохраняет ID, email, имена, статусы, роли и готовые PBKDF2-хэши без
повторного хэширования. Последовательность ID настраивается после последнего перенесённого
пользователя. Перед обновлением с более ранней версии сначала примените `021-security`.

Импорт транзакционный: конфликт ID/email останавливает запуск и откатывает перенесённые
строки, не перезаписывая существующие аккаунты. Успешный импорт отмечается в `user_imports`
и при повторном запуске не выполняется. При чистой установке отсутствующий источник
пропускается. После проверки переноса можно задать `USER_MIGRATION_SOURCE_URL=` в `.env`,
чтобы отключить доступ к старой базе на следующих запусках.

Миграция `022-extract-users` удаляет межсервисные внешние ключи и переименовывает старую
таблицу `users` в `legacy_users`. Архив сохраняется для проверки и восстановления; рабочее
приложение его не читает и не обновляет. Старые миграции не переписываются. Удалять архив
можно отдельной миграцией после сверки данных и резервного копирования.

Из-за перехода на RS256 старые HS256-токены перестают подходить: после обновления войдите
заново. Потеря volume `user-signing-keys` также потребует нового входа.

## Вход и Swagger

```bash
TOKEN=$(curl -fsS http://localhost:8080/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"supervisor@example.com","password":"replace-with-a-strong-password"}' \
  | jq -r '.access_token')

curl -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/v1/auth/me
```

Успешный вход возвращает `access_token`, `token_type: "Bearer"` и `expires_in` в секундах.
`GET /api/v1/auth/me` возвращает текущего пользователя с ролью, без пароля или его хэша.

Общий Swagger: http://localhost:8080/swagger-ui.html. В списке документов выберите
`user-service`, найдите группу `Authentication` и выполните `POST /api/v1/auth/login`.
В **Authorize** вставьте только JWT, без слова `Bearer`. При переключении на документацию
другого сервиса проверьте, что токен установлен и для неё. Документы всех API содержат
схему безопасности `bearerAuth`.

Публичны вход, Swagger/OpenAPI, открытый JWKS и healthcheck. Все остальные пользовательские API требуют токен.
Health-ручки соседних сервисов из предыдущей работы доступны супервайзеру.

## Роли и доступ к данным

| Действие | SUPERVISOR | OPERATOR | VIEWER |
|---|---|---|---|
| Создать пользователя, изменить его роль/статус, удалить | Да | Нет | Нет |
| Посмотреть список пользователей | Да | Нет | Нет |
| Посмотреть свой профиль | Да | Да | Да |
| Посмотреть список проектов | Все проекты | Свои и с участием | Свои и с участием |
| Читать проект, его мониторы, инциденты, историю, каналы, уведомления | Все | При наличии доступа к проекту | При наличии доступа к проекту |
| Создать проект | Для любого владельца | Только для себя | Нет |
| Изменять мониторы, каналы, закрывать инциденты | Все | В доступных проектах | Нет |
| Изменять/удалять проект, управлять участниками и настройкой уведомлений владельца | Все | Только владелец проекта | Нет |
| Создавать теги | Да | Да | Нет |
| Удалять общие теги, проверять состояние сервисов | Да | Нет | Нет |

Например, один и тот же `GET /api/v1/projects` у супервайзера возвращает все проекты,
а у оператора или просмотрщика — только доступные им, с пагинацией и корректным общим
количеством. Передача чужого ID в URL не даёт доступ к чужому ресурсу. Членство в проекте
не даёт просмотрщику права записи, а роль оператора сама по себе не открывает чужие проекты.

Создание пользователя супервайзером:

```bash
curl -i http://localhost:8080/api/v1/users \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"email":"operator@example.com","password":"operator-password","full_name":"Operator","role":"OPERATOR"}'
```

Если роль не указана, назначается `VIEWER`. Изменить её можно только супервайзеру через
`PUT /api/v1/users/{id}/role` с телом `{"role":"OPERATOR"}`.

`POST /api/v1/auth/register` — дополнительный путь создания пользователя с теми же правилами:
он требует JWT супервайзера, возвращает HTTP 201 и `Location`. Самостоятельная регистрация
без супервайзера недоступна. Удаление пользователя мягкое: аккаунт становится неактивным
и скрывается из пользовательского CRUD, а его ID сохраняется для владельцев и участников проектов.

## Хранение паролей и JWT

Пароли хэшируются PBKDF2-HMAC-SHA256 со случайной солью стандартным
`Pbkdf2PasswordEncoder.defaultsForSpringSecurity_v5_8()`. Формат содержит идентификатор
алгоритма для будущего обновления. PBKDF2 позволяет сохранить поддержку паролей длиной
до 255 символов без ограничения BCrypt в 72 байта.

Миграция `021-security` хэширует все существующие открытые пароли, переименовывает колонку
в `password_hash` и добавляет строковую роль `VIEWER`. Старые пароли продолжают подходить
для входа. Хэширование необратимо: rollback схемы не восстанавливает открытые пароли.
Модели ответов пользователя не содержат ни пароль, ни хэш; поле сущности дополнительно
защищено `@JsonIgnore`, входные пароли помечены как write-only.

JWT подписывается RS256 только в user-service. Проверяются подпись, issuer, audience,
срок действия и not-before. Gateway и сервисы получают открытый ключ через
`/.well-known/jwks.json`; закрытые параметры в JWKS не возвращаются.
Идентификатор пользователя хранится в `sub`, роль — в `roles`. По умолчанию токен действует
15 минут. Refresh-токены в этой работе не используются: после истечения срока нужен новый
вход. Секретный ключ не хранится в БД или выдаваемом клиенту токене.

В user-service статус и роль перечитываются из его БД; monitor-service запрашивает
актуальные сведения через защищённый Feign API. Поэтому
блокировка, удаление или понижение роли действуют и для ранее выданного JWT. Проверки
доступа из check-service/notification-service также используют актуальные данные БД.
Gateway проверяет роль из самого токена; после повышения роли следует войти повторно,
чтобы получить новый JWT с новыми правами.

## Межсервисные вызовы

Проверка JWT выполняется и в gateway, и в сервисах. Gateway передаёт пользовательский
Authorization дальше. Для вызовов через Feign сервис получает отдельный короткоживущий JWT
с ролью `SERVICE` в user-service; пользовательские токены эту роль получить через API не могут.
Это позволяет планировщикам и обработчикам событий работать без пользовательской сессии.

Для выдачи служебного JWT используется `POST /internal/auth/token` с `client_id` и
`client_secret`. Это внутренний API проекта, не полная реализация OAuth Authorization Server.
Секреты клиентов хэшируются в `service_clients`. Настройки окружения применяются при запуске
и позволяют заменить секрет без изменения кода. Клиенту всегда назначается только `SERVICE`;
произвольную пользовательскую роль запросить нельзя. Токен действует 5 минут по умолчанию
и кэшируется клиентом до обновления. Отдельный HTTP-клиент для получения токена исключает
рекурсивный вызов Feign-интерцептора.

Выдача служебного токена проверяет учётные данные клиента и не требует уже выданного JWT.
Остальные `/internal/**` принимают только служебную идентичность и не маршрутизируются gateway.
Служебный JWT не разрешает обращаться к пользовательскому API. Check-service и
notification-service отправляют в защищённую внутреннюю ручку monitor-service ID из
проверенного пользовательского JWT и ID ресурса. Monitor-service проверяет актуальную роль,
статус пользователя через user-service и принадлежность проекта в своей БД. При недоступности
проверки доступ не выдаётся; HTTP 503 отличается от неверных учётных данных (401).

## Ошибки и проверки

- HTTP 401: отсутствующий, просроченный или неверный JWT; неправильный пароль; заблокированный пользователь.
- HTTP 403: JWT действителен, но роли или доступа к ресурсу недостаточно.
- HTTP 503: недоступен сервис, который проверяет права на ресурс.

Ответы об ошибках авторизации имеют формат `application/problem+json` и не содержат
паролей или внутренних деталей проверки.

```bash
./gradlew check
export SUPERVISOR_PASSWORD='то-же-значение-что-в-.env'
./scripts/auth-demo.sh
```

Скрипт проверяет через gateway вход, отсутствие паролей в ответах, создание пользователей
только супервайзером, права оператора/просмотрщика и доступ к истории и каналам в других
сервисах. Он создаёт отдельные демонстрационные аккаунты и проект для каждого запуска.
Существующие `demo.sh` и `circuit-breaker-demo.sh` тоже используют JWT: передайте `TOKEN`
или экспортируйте `SUPERVISOR_PASSWORD` и, при необходимости, `SUPERVISOR_EMAIL`.

Автоматические тесты дополнительно проверяют подпись/issuer/срок JWT, миграцию старых
паролей на PostgreSQL, роли и членство для разных ресурсов, блокировку уже выданных токенов,
служебную аутентификацию и кэш токенов, сохранение закрытого ключа при перезапуске,
проверку подписи по HTTP JWKS, транзакционный импорт пользователей, закрытый доступ
при сбое проверки прав и Bearer-схемы Swagger.

Использован стандартный механизм Spring Security Resource Server:
[Servlet JWT](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html),
[Reactive JWT](https://docs.spring.io/spring-security/reference/reactive/oauth2/resource-server/jwt.html).
